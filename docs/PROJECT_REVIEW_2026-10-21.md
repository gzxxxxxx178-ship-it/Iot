# 全目录项目审阅与优化建议

审阅日期：2026-10-21。范围：当前 Git 工作区的各子项目、主要业务链路、测试、构建和部署脚本。开始时工作区干净。本轮只新增审阅文档与问题台账记录，不修改业务实现，不推送或部署。

## 判断

项目已经形成“设备采集—持久化—规则评估—命令审计—多端展示”的工程骨架，并将真实设备、MATLAB 仿真和冻结研究结果分域管理。现阶段应优先修复权限、数据质量和命令状态一致性，再完善发布门禁；暂不需要拆微服务、替换数据库或扩充算法种类。

测试全部通过，但仍有未覆盖的跨线程、跨事务、多用户和真实基础设施边界。下面区分代码直接确认的问题、由执行顺序推导的竞态风险，以及尚未现场验证的能力。

## 优先级与建议

P0：权限边界，应最先处理。P1：正确性与可靠性，下一轮处理。P2：维护、性能与能力边界，前述修复后推进。所有建议保持待执行，不因本轮审阅自动实施。

### REV-01 / P0：取消普通用户自动认领全部无主设备

- **证据**：`java/src/main/java/com/ruoyi/iotsystem/service/DeviceService.java:256` 的 `claimLegacyDevices` 查询全部 `ownerUsername IS NULL` 设备，逐一归给调用账号，并更新无主历史数据。设备列表、详情和部分管理请求会调用它；自动发现设备也可能产生无主档案。
- **影响**：任何已登录普通账号都可能成为无主设备的首个访问者，从而取得设备及历史归属。这是代码确认的权限边界问题；本轮未对真实账号或数据库执行认领验证。
- **建议**：将历史归属迁移移出普通请求，改为人工审核的一次性迁移；新设备使用设备绑定凭证或明确授权流程，未绑定时不可控制。
- **验收**：账号 B 访问列表、详情、历史时不能认领无主设备；数据库归属保持不变；合法绑定需证明绑定权限，并防止并发重复认领。

### REV-02 / P1：修复 Redis 配置绑定

- **证据**：`java/src/main/resources/application-prod.properties:18` 及默认配置使用 `spring.data.redis.*`，当前 Spring Boot 版本为 2.7.18。已直接读取本机对应依赖包的配置元数据，`RedisProperties` 前缀为 **`spring.redis`**。
- **影响**：上述 host、port、password、timeout 等连接配置不会绑定到当前版本的自动配置；Redis 可能退回默认连接。测试使用 Redis 替身，不能检出这类错误。默认配置还声明 Jedis 池参数，应同时核查实际采用的连接客户端。
- **建议**：按当前版本修正配置前缀，增加不连接网络的配置绑定测试；后续升级框架时单独迁移配置，避免混用版本语法。
- **验收**：为非默认 host/port/password/timeout 设置测试值，断言实际绑定结果；对池参数与客户端选择做同样检查。
- **官方依据**：[Spring Boot 2.7 Redis 配置说明](https://docs.spring.io/spring-boot/docs/2.7.17/reference/htmlsingle/index.html)。

### REV-03 / P1：禁止无效遥测静默变为零值

- **证据**：`java/src/main/java/com/ruoyi/iotsystem/service/MqttMessageService.java:246` 使用 `has(...)` 后调用 `asDouble()` 等转换。使用项目 Jackson 2.13.5 实测，字段为 `null`、`"bad"`、`{}` 时，`has=true` 且 `asDouble=0.0`。
- **影响**：这些值落入 `EspService` 的部分合法数值区间，可能被记为有效数据并进入报警或自动化评估，违反“异常数据不触发规则”的设计。
- **建议**：先验证 JSON 类型与非空，再转换；缺测与错误值保留明确质量标记。只有明确允许兼容的数值字符串才做受控转换。
- **验收**：覆盖缺失、null、字符串、对象、数组、非有限值和越界值；异常记录不得作为有效零值触发自动化。

### REV-04 / P1：解决命令下发与 ACK 的事务竞态

- **证据**：`java/src/main/java/com/ruoyi/iotsystem/service/DeviceCommandService.java:26` 在同一事务内保存 `PENDING`、发布 MQTT、改为 `DISPATCHED`；`acknowledge` 只接受已可见的 `DISPATCHED`。实体没有版本字段，超时扫描也使用读后写。
- **风险推导**：人工控制路径中，快速 ACK 可能早于下发事务提交，因查不到记录或状态不匹配被丢弃；ACK 与超时并发也存在终态覆盖窗口。本轮未搭建 Broker 并发复现场景，不能据此声称线上已经发生。
- **建议**：先提交命令意图，再由可靠派发流程发布；根据规模选择事务事件加重试，或事务发件箱。ACK、拒绝、超时用条件更新或乐观锁维护状态机，并定义早到/迟到回执处理规则。
- **验收**：在提交前注入 ACK、并发 ACK/超时、重复 ACK 和派发进程中断场景下，命令状态及审计一致；数据库回滚不能留下无法追溯的已执行命令。

### REV-05 / P1：自动化记录关联真实命令终态

- **证据**：`AutomationService.executeAction` 将下发时的命令状态和含 `commandId` 的消息复制到 `AutomationExecutionEntity`。执行列表直接返回快照；`DeviceCommandService.acknowledge` 和超时扫描只更新命令表。Vue 与小程序仅显示执行记录的 `status`。
- **影响**：命令已确认、拒绝或超时后，自动化执行记录仍可能永久显示 `DISPATCHED`；前端增加状态文字映射不能解决后端状态来源问题。
- **建议**：执行记录用结构化 `commandId` 关联命令，在查询时返回最新状态，或在状态流转中同步更新；通知事件与设备命令使用明确不同的成功定义。
- **验收**：自动化触发后分别模拟 ACK、REJECTED、TIMED_OUT，执行列表与命令审计终态一致。

### REV-06 / P1：统一共享设备的查询和实时授权

- **证据**：`DeviceService.visibleDevices`、历史查询支持共享账号；`SensorWebSocketHandler.java:34` 仅推送给设备所有者。`MqttMessageService` 调用时也只传所有者，未传设备 ID 以解析共享授权。
- **影响**：共享账号可在列表看到设备、按设备读取历史，却收不到相同设备的实时遥测；轮询可能掩盖问题。
- **建议**：按设备 ID 解析当前可读账号，推送前校验共享权限；撤销共享后立即停止推送。增加每会话发送串行化及慢客户端隔离，避免同步发送拖住 MQTT 消费线程。
- **验收**：所有者、共享者均收到授权设备消息；第三账号收不到；撤销共享后已有连接也不能再收到该设备数据。

### REV-07 / P1：收紧固件命令解析、去重和回执语义

- **证据**：`arduino/MQTT/MQTT.ino:135` 用字符串查找解析 JSON，要求固定的无空白键值格式；带 `commandId` 的未知命令也会落到统一 `ACKNOWLEDGED` 分支。未保存已处理命令 ID，回执发布返回值未检查。`start/stop` 仅切换 `isSending`，当前固件没有泵阀驱动实现。
- **影响**：等价 JSON 格式可能解析失败；无效命令可被误确认；重复投递可能重复执行 `read` 或重置计数。采集启停也不能作为泵阀动作完成证据。
- **建议**：采用受限内存的 JSON 解析，明确白名单与 `REJECTED`，以最近命令 ID 做有界去重；对 ACK 发送失败设计重试。界面与协议将当前动作标成“采集启停”，未来真实执行器另建反馈字段。固件依赖、板卡版本和证书轮换流程应可复现。
- **验收**：覆盖字段顺序/空白变化、畸形 JSON、未知命令、重复 ID、断网回执；台架只验证安全的状态/读取指令。泵阀能力需独立硬件反馈验收。
- **依据**：当前回执调用的 API 没有 QoS 参数；PubSubClient 的发布可靠性应以其[官方 API](https://pubsubclient.knolleary.net/api)和[实现](https://github.com/knolleary/pubsubclient/blob/master/src/PubSubClient.cpp)为准，不能把订阅 QoS 1 等同于设备回执可靠送达。

### REV-08 / P2：统一网页 HTTP 与 WebSocket 默认地址

- **证据**：`vue/IoT/src/api/request.js` 在开发环境默认请求 `http://localhost:8080`；`src/composables/useWebSocket.js:28` 在没有环境变量时使用 `window.location.origin`。Vite 配置没有 `/ws` 代理。
- **影响**：按默认开发方式运行，REST 可成功而 WebSocket 指向 5173 前端服务，实时链路失败。
- **建议**：抽出统一地址解析，或在 Vite 中统一代理 HTTP 与 WebSocket；Cloudflare 的固定上游地址改为受控环境配置。
- **验收**：无环境变量时本地两条链路均正常；同源生产、独立 API 域名及显式 WS 地址分别验证。

### REV-09 / P2：减少列表请求中的扫描和 N+1 查询

- **证据**：设备列表每次先对历史表查全部不同设备 ID，再对每设备查最新一条数据；研究列表先加载全部 run，再在 Java 中截取 `limit`，每个返回 run 又单独查指标。
- **影响**：查询次数随设备/运行数增长。5 秒采样时，单设备每天约 17,280 条、365 天约 630.72 万条；此为容量推算，**不是当前实测规模**。
- **建议**：历史补录移出热路径；设备最新状态采用批量查询或独立最新状态表；研究列表在数据库分页，详情按需加载指标。按实际查询计划评估索引和分批保留期清理。
- **验收**：记录基线与修改后的 SQL 数量、响应时间和查询计划；列表 SQL 次数不能随设备数逐条增长，研究 `limit` 必须下推数据库。

### REV-10 / P2（真实收款前必须完成）：补齐支付订单一致性校验

- **证据**：`AlipayService.handleNotify` 验签后按订单号与 `TRADE_SUCCESS` 更新状态，没有核对本地订单金额、`app_id` 和卖家身份；当前默认 gateway 是支付宝沙箱。
- **边界**：这里确认的是沙箱实现缺项，不代表已发生资金损失，也不将该模块视为生产支付能力。
- **建议**：优先用功能开关隔离沙箱；若保留支付，增加订单金额/应用/卖家匹配、条件更新、回调幂等和失败审计，补齐支付测试。
- **验收**：签名合法但金额、应用或卖家不匹配的通知不改变订单；重复通知不重复履约；未知订单不能被当作本地成功入账。
- **官方依据**：[支付宝异步通知校验要求（阿里巴巴开放平台）](https://developer.alibaba.com/docs/doc.htm?articleId=105302&docType=1&treeId=204)。

### REV-11 / P2：限制视觉 MCP 的文件读取与外发范围

- **证据**：`mcp-servers/zhipu-vision/index.js:229` 依据扩展名选择 MIME，未知扩展名默认 PNG，然后同步读取整个文件并发送外部 API；没有实际文件类型、大小或授权目录校验。
- **影响**：调用方传入的非图片或超大文件也会被读取和外发。此工具按设计具备图片外发能力，需要把边界落实到文件验证。
- **建议**：验证文件魔数、大小、普通文件属性；配置允许目录并检查符号链接后的真实路径；对输入行、上游响应和并发请求设上限。
- **验收**：文本改扩展名、超限文件、目录、越界路径及符号链接越界均在网络请求前拒绝，正常图片仍可处理。测试使用本地替身，不消耗真实 API。

## 科研与农机农艺耦合建议

- 保留当前“合成 SIL、未田间标定”的边界。真实设备 `water` 是 0–1023 ADC，实验水深为 mm，当前不能直接换算；推进实际控制前，需要传感器标定、安装位置、有效量程、异常工况以及泵流量/延迟测量。
- 当前 SAC 冻结实验明确没有改善 MPC，应保留失败对照。下一轮先补参数/预报误差协议、独立训练随机种子与验证方案；不能针对已查看的测试结果继续调参后沿用原测试集宣称无偏性能。
- MPC 使用有限窗口完美预报，田间适用性需预报误差试验与作物生育期目标约束支持。模型的水位目标和安全区间不能直接成为农艺处方。
- Python 与 Java RAG 语料本轮逐字节一致，这是已有优势；应再加入自动快照摘要校验和两端固定问题集回归，防止分词、计分或拒答规则漂移。内部 16 题 test 与开发期接触记录不足以支持外部通用效果宣称。
- 冻结结果保留已有 manifest，再逐步增加代码提交、配置摘要、输入/输出文件哈希和运行环境；历史冻结产物不为提高指标而修改。新评估单独登记，不覆写旧结论。
